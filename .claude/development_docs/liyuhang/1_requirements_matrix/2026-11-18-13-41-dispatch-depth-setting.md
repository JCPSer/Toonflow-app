# 需求矩阵：Agent 任务链上限开放为开发者设置

- 时间：2026-11-18 13:41
- 范围：`sendToAgent` 的 8 跳硬上限 + 画布 dispatcher 的 `MAX_DEPTH = 8` 兜底

## 需求背景

任务链深度上限目前写死为 8（服务端 `MAX_DISPATCH_DEPTH`、画布 `MAX_DEPTH`）。用户希望能在设置页「开发者选项」里调整，避免为改一个数字重新构建，也便于排查派发链路。

## 需求目标

1. 开发者选项新增「任务链上限」，范围 1–32，默认 8。
2. 服务端工具与画布 dispatcher 使用同一个设置值，不出现两套口径。
3. 保存后对新派发生效；未配置时行为与现在完全一致（8）。
4. 非法值（0、负数、非数字、超范围）按范围钳制，不保存脏值。

## 需求描述

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | 设置项 | 开发者选项新增数字输入，1–32 跳，默认 8，附「下一条消息生效」说明。 |
| R2 | 服务端生效 | `sendToAgent` 的拒绝文案使用实际上限；超过时仍直接报错，不派发。 |
| R3 | 画布生效 | dispatcher 的兜底判断改用设置值，防止旧客户端或手工事件绕过。 |
| R4 | 口径一致 | 两端读取同一字段 `developer.dispatchMaxDepth`；缺失/非法回落到 8。 |
| R5 | 不改变语义 | 结果回传不增加深度；超限仍是工具错误，不自动降级。 |

## 优先级

P2（可调参数；不阻塞既有功能）。

## 需求难度

低。设置存储、一个输入框、两处读取点、单测。

## 需求风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 设得过大导致链路失控 | 成本与等待时间不可控 | 上限封顶 32；描述里说明「越大越难追踪」 |
| 服务端与画布读值时机不同 | 中途改设置导致行为不一致 | 服务端每次派发读取一次；画布每次入队读取一次；说明「下一条消息生效」 |
| 旧会话没有该字段 | 读取异常 | 统一 `normalize` 回落默认 8 |
| 远程/移动端设置页不同步 | 只在桌面可见 | 沿用现有开发者设置的存储与同步机制，不新增通道 |

## 验收标准

1. 默认（未配置）时，第 9 跳仍被拒绝，文案为「8 跳上限」。
2. 改成 3 后，第 4 跳被拒绝，文案为「3 跳上限」；第 3 跳可正常派发。
3. 输入 0 / 100 / 空值保存后落到 1 / 32 / 8。
4. 服务端与画布行为一致；服务端单测、web 构建通过。
