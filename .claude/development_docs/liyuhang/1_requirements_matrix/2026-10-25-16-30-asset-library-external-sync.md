# 需求矩阵：素材库与磁盘保持一致（外部改动自动同步）

- 时间：2026-10-25 16:30
- 来源：用户需求「素材库能否在硬盘上保持目录结构一致？方便在系统文件管理器直接管理，检测到文件变动后同步即可，要做好性能优化」

## 现状核查（已完成）

| 项 | 现状 | 结论 |
| --- | --- | --- |
| 磁盘结构 | 全局库 `<数据目录>/assets/**`，项目库 `<项目>/library/**`（被占用时 `library-assets`） | **已经 1:1**，界面层级就是真实目录 |
| 读取方式 | `list/tree` 每次实时 `opendir + lstat` | 外部新增/删除在下次读取时就生效，不需要"导入" |
| 隐藏目录 | `.library`（标记 + `index.json`）、`.trash`（回收站）、`.thumbs` 已被 `internalAssetDirectories` 排除 | 不参与展示 |
| 元数据 | `index.json` 以**相对路径**为 key 存标签/备注/收藏 | 外部改名/移动 → 元数据丢失（reconcile 建新条目 + prune 删旧） |
| 变动通知 | 无监听、无推送；只有手动刷新 / 切目录 / 写操作后刷新 | 外部改动不会自动出现 |
| `stale` 字段 | 有类型和归一化，但全仓库**没有任何地方写入**，也没透出给前端 | 需要真正实现 |
| 引用检查 | `usage.ts` 是"素材 → 引用方"方向，只在删除时调用 | 无法发现"引用指向已删除素材" |

## 需求矩阵

| 编号 | 需求 | 目标 | 优先级 | 难度 | 风险 |
| --- | --- | --- | --- | --- | --- |
| R1 | 磁盘结构 1:1 | 保持现状；不新增可见的辅助文件，隐藏目录仍然只有 `.library/.trash/.thumbs` | P0 | 低 | 误在库根写缓存文件 |
| R2 | 外部变动自动刷新 | 素材库可见时开递归监听，300ms 防抖；只刷新受影响的当前目录；目录增删才重建树 | P0 | 中高 | 上传/缩略图生成会触发自身事件，形成刷新风暴 |
| R3 | 元数据跟随文件 | 索引记录 `dev+ino`；外部改名/移动后标签/备注/收藏跟着文件走；旧索引自动补 inode | P0 | 中 | inode 复用导致元数据错挂；索引条目多时 inode 映射成本 |
| R4 | 外部删除的引用可见 | 列表额外返回"索引有、磁盘无"的缺失条目并标 `missing`；界面上提示，不自动改引用 | P1 | 中 | 缺失条目需要与搜索/分页/截断互斥 |
| R5 | 性能 | 树子项数并发 4 + 2s 缓存；事件刷新合并 500ms；列表对同一目录 500ms 内复用扫描结果 | P1 | 中 | 缓存导致"改了看不到" |

## 用户已确认

| 问题 | 结论 |
| --- | --- |
| 变动发现方式 | 文件监听 + 防抖，只推送"当前目录变了" |
| 改名后的标签 | 跟随文件（inode） |
| 外部删除被引用素材 | 标缺失 + 提示，不自动动引用 |

## 不做（本轮）

- 不做"引用方 → 素材是否存在"的全量校验（需要遍历所有画布与会话，成本高，另立需求）。
- 不迁移回收站到可见目录（`.trash` 仍隐藏，用户在 Finder 里删文件视为真删）。
- 不做跨库 inode 去重（同一文件被复制到两个库就是两份独立素材）。
