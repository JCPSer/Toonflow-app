# 记忆：H3 首尾帧条件图被纵向拉伸约 1%

- 时间：2026-11-03 03:08
- 类型：外部 Provider 配置修复（不在本仓库）

## STAR

**Situation（背景）**
用户反馈：用尾帧接下一段时画面跳变，剪辑软件里下一段的 Y 轴总比上一段高约 1%，要在上一帧上手动拉 1% 才对得上；怀疑是首尾帧截取在 Y 轴有问题，或接口问题。

**Task（任务）**
先判定「截取侧」还是「模型侧」，再修。

**Action（行动）**
- 截取侧取证：同一工程的帧与视频都是 1920×2560，逐像素 PSNR 72.3 dB；人为加 1px 纵向偏移后降到 49.0 dB → 无偏移、无缩放。
- 模型侧取证：把「送进去的首帧」与「生成视频第一帧」做比例扫描。只缩放 Y 时 PSNR 在 1.008–1.010 倍达峰（38.5/39.6 dB，1.000 时 30.6/34.9 dB）；只缩放 X 时一路变差 → 各向异性纵向拉伸，约 1%，两条时间线都复现。
- 根因：`/Applications/toonflow-data/providers/minimaxH3RefFrameLocal.ts` 的首/尾帧用 `LayerUtility: ImageScaleByAspectRatio V2`（总像素 1280k、`round_to_multiple: 32`，该参数是**向上取整**）预处理。1920×2560 → 979×1306 → 992×1312，比例由 0.7500 变 0.7561（宽 +0.81%）；生成画布是 3:4 的 960×1280（×2 超分＝1920×2560），条件图铺满画布后即纵向约 0.8% 拉伸。
- 修复：把 236（首帧）/231（尾帧）换成文件里参考视频槽位同款 `ImageResizeKJv2`（width/height 接 164 节点、`keep_proportion: crop`、`divisible_by: 16`），条件图与生成画布严格同比例，最多裁掉 0.4% 边缘，不拉伸。已备份为 `.bak.20261103030849` 并做 TS 语法检查。

**Result（结果）**
文件已改，**未重启应用**；需用户重启后重新生成一条片段，用同一套 PSNR 扫描复测，峰值应回到 1.000。

## 关键经验

1. 「看起来像缓存/接口」的画质问题，先量：同一帧做比例扫描，比肉眼和猜根因都快。
2. `round_to_multiple` 是向上取整，不同方向各取一次就会改变比例；要锁比例就用「按目标宽高裁切」而不是「按总像素缩放到 32 的倍数」。
3. 这类失真会被后续每一段继承，剪辑时表现为逐段累积的位移，不是单段瑕疵。
4. 其余三个 H3 provider（FirstLastFrame / SingleImage / Local）仍是同一套 LayerStyle 预处理，未改。
