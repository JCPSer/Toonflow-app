# Bug 分析：画布 Agent 面板重开后，输入框 ↑/↓ 选不了历史

- 时间：2026-10-30 00:40
- 提出人：liyuhang
- 模块：`apps/web/src/components/agent/conversation/`
- 代码基线：`0e5fda5` + 上一轮分组贴合改动（未提交）

## 1. 背景与现象

画布上的 Agent 节点面板，关闭后再打开，输入框按 ↑/↓ 完全没反应，翻不出会话里的历史消息；用户描述"只能选当前生命周期对话的历史消息"。重开后面板的消息列表显示正常（和关闭前一样），没有任何 toast/报错。

## 2. 复现与定位过程

在浏览器客户端连应用 HTTP 端口，用真实会话（单会话 59 条用户消息）逐条验证：

- 空着关 → 重开 → ↑：正常翻出旧消息，可一路翻到最旧一条；
- 带草稿关（实例被保留）→ 重开 → 清空草稿 → ↑：正常；
- 换节点、切画布、整页刷新手测均正常。
即：**基础链路成立，问题只出现在某些状态被"卡住"之后**，需要在代码里找"状态残留"路径。

定位到两处会造成"永久性无响应"的缺陷：

### 2.1 幽灵提及（主因，已用日志复现）

`draftMentions` 只在发送（`clearDraft`）、程序化填充（历史还原 / 插入提及 / 回退填充 / 编辑草稿恢复）时更新；**用户把输入框里的 `@` 提及标签删掉（退格、整段删除）后，数组不会回收**（`removeDraftMention` 只是从数组删，反向的"标签没了"没有任何监听）。影响：

- `draftEmpty()` = 文本空 && 提及 0 && 附件 0 → 幽灵提及让它永远为 false，`handleHistoryKey` 在 `historyIndex === null` 分支直接 return，↑ 完全不响应（没有任何反馈）；
- `hasDraft()` 同样依赖数组 → 面板关闭时认为"还有草稿"，**实例不卸载**。重开面板拿到的是同一个坏实例，幽灵提及还在，于是"关掉再开还是不行"；
- 发送一次会 `clearDraft` 清空提及 → 历史又恢复，用户感知就是"只能选当前生命周期（重新发送之后）的消息"。

注意因果顺序：**幽灵提及是在关闭之前就生成的**——也就是说关闭前 ↑ 其实已经失效，用户只是"重开后第一次去按 ↑"。修复里 `draftEmpty()` 负责让 ↑ 恢复，`hasDraft()` 负责让坏状态能在关闭时被清掉、不再跨重开继承。

日志证据（临时插桩）：清空输入后 `text:""` 但 `mentions:1`、`empty:false`，↑ 无反应。

### 2.2 历史还原串行队列与在途任务（防御性加固，未复现）

`historyQueue = historyQueue.then(任务)` 串行执行还原；任一任务不返回，后续 ↑/↓ 都排不上。现有两个 await（`reset` → rAF、`instance.nextTick`）在组件存活时都会 resolve，**没有复现到真正的永久卡死**，因此只做防御：面板收起时复位队列并推进代次，代次用于拦住"收起瞬间仍在途"的旧还原把旧消息写回重开后的输入框。

## 4. 修复口径

- 提及以**编辑器里真实存在的标签**为唯一真源：`draftEmpty()` / `hasDraft()` / `composable` 都查标签集合；change 事件维护这份集合。
- **不回收 `draftMentions`**：数组保持超集。直接删会被"⌘Z 撤销删标签"打穿——x-sender 的撤销快照只重建 `{id,name}` 标签，数组补不回来，发送时会被"存在无法读取的提及"拦下；发送侧本来就按 `getTagData()` 的下标过滤，多余项不会外发。
- `draftEmpty()` / `hasDraft()` / `handleHistoryKey` 在 `historyFilling`、`insertingMentions` 期间都要豁免：中途标签未落盘，判空会误判、还原会打断正在插入的提及。
- 面板收起（`active=false`）时复位 `historyQueue` 并推进 `historyEpoch`，清掉 `mentionQuery`/`skillQuery`。

## 5. 验收标准

- 正常会话：开启/关闭/重开面板，↑/↓ 均能翻到会话最早一条。
- 翻出带 `@` 提及的历史后，把输入框清空，↑ 立即可用（不再被幽灵提及挡住）。
- 带草稿关闭面板，重开时草稿保留；清空草稿后 ↑ 可用。
- 程序化填充历史、插入提及/附件后，提及数组与编辑器标签一致，发送时提及不丢。
