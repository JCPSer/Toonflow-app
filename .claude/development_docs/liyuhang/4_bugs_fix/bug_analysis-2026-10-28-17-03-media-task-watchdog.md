# bug 分析：生成任务被「页面长时间未连接」误杀

- 记录时间：2026-10-28 17:03
- 报告现象：任务在正常跑，却报「生成任务因页面长时间未连接而停止」
- 代码基线：`1342529` + 工作区未提交的运行时长改动（与该 bug 无关）
- 修复决策：**直接去掉 120s 看门狗**；附带**页面可见时立即补一次心跳**

## 一、现象

用户提交图片/视频/音频生成后，页面侧任务并没有取消、供应商也仍在正常出图，但界面报出「生成任务因页面长时间未连接而停止」，任务被判失败。

关键矛盾：**用户全程开着页面，任务也确实在跑**，但服务端认为「页面已断开」。

## 二、根因

`apps/server/src/modules/mediaGeneration/media/tasks.ts` 里有一条服务端看门狗：

```
cleanup() 每 30 秒跑一次：
  若任务未结算，且 touchedAt + 120000 <= now
    → stop(task, "生成任务因页面长时间未连接而停止")
```

`touchedAt` 只在一处刷新：`status(cwd, taskIds)`（`tasks.ts:52`），也就是前端 `/api/ai/media/tasks/status` 的轮询。

前端轮询在 `packages/nodeScaffold/src/nodeAi.ts:103-171`，用 `setTimeout` 串联（`schedule()` / `poll()`，间隔 1000ms）。

**失败链条**：

1. 媒体生成是长任务，用户切走窗口、把应用放后台、或系统进入节能态时，WKWebView 会节流 `setTimeout`（后台定时器被压到分钟级，甚至暂停）。这在 macOS 低电量模式下已实测过会压低帧率与定时器频率（见记忆 `2026-10-26-18-30`）。
2. 于是 `poll()` 停止触发，`touchedAt` 在服务端不再刷新。
3. 服务端 `cleanup()` 与前端轮询之间没有任何「页面是否还活着」的独立信号，只看 `touchedAt`。
4. 满 120 秒 → `stop()` → `controller.abort()` → 供应商请求被中止，任务结果写成 499。

所以这不是「页面真的断了」，而是**把「前端定时器是否按时跑」当成了「页面是否还在」**。两个概念不等价。

## 三、设计缺陷评估

| 缺陷 | 说明 |
| --- | --- |
| 用轮询节拍代替存活判定 | 定时器被节流 ≠ 连接断开。健康检查应该基于连接本身（SSE/WebSocket 断开、进程退出），而不是业务轮询频率 |
| 与供应商真实耗时冲突 | 视频生成本身可能超过 120 秒，一次后台切换就足以误杀已付费的任务 |
| 前端已有更强的兜底 | `nodeAi.ts:160-163` 已经实现了「状态查询失败累积 90 秒才判失败」，同样的目的不应在服务端再叠一层更激进的判定 |
| 误杀代价高 | 生成已提交给供应商、费用已产生，中途 abort 得不到结果，用户只能重跑再花一次钱 |

## 四、修复方案选型

| 方案 | 做法 | 评估 |
| --- | --- | --- |
| A（选定） | 删掉 120s 看门狗 | 任务只因**用户取消**或**供应商失败**结束。页面真崩时任务会继续跑直到供应商超时，结束后 5 分钟自动清理（`settledAt + 300000`），不会永久泄漏 |
| B | 页面可见时不计超时 | 需要前端传可见性心跳，链路更长，且仍需一个「多久算真断」的新阈值 |
| C | 只调大阈值 | 治标。视频生成超 30 分钟仍会误杀 |

选 A 的核心理由：**留存一个不会误判的缺失，好过一个会误杀的错误**。

## 五、附带修复

页面从后台切回可见时立即补一次轮询（`visibilitychange`），不等下一个 1 秒周期。这样后台期间被节流的这段时间，切回来立刻对齐状态，感知延迟从最长 1 秒降到 ~0。

## 六、影响面

- `apps/server/src/modules/mediaGeneration/media/tasks.ts`：删看门狗分支与 `touchedAt` 字段。
- `packages/nodeScaffold/src/nodeAi.ts`：新增可见性补轮询。
- 前端 90 秒断线容错窗口**保持不动**（用户明确选择只做可见性补心跳）。这意味着如果页面真的断网超过 90 秒，前端仍会自己判失败并通知服务端取消——这条路径是合理的，它基于「请求真的失败了」，不是基于「定时器没响」。

## 七、回归风险

| 风险 | 评估 |
| --- | --- |
| 页面崩溃后任务无限占用 | 不成立：任务会在供应商返回/超时后 `settledAt`，5 分钟后清理。上限 1000 个任务（`tasks.ts:38`）也仍在 |
| 用户关闭窗口后供应商仍计费 | 这是既有行为（原设计用 120s 试图兜住），改为只依赖 provider 端超时。需在文档中说明这一取舍 |
| `touchedAt` 删除后是否有其他读取方 | 已确认：只有 `cleanup()` 读它，`status()` 只写它 |

## 八、验收标准

1. 提交一次图片生成，把窗口切到后台超过 3 分钟再切回，任务仍能拿到结果，不出现「页面长时间未连接」。
2. 页面切回可见时，状态最多 1 秒内刷新（原为最长 1 秒 + 后台节流延迟）。
3. 主动取消任务，仍能立刻中止并报「生成已取消」。
4. 主动关闭页面后不再有新的轮询，任务不因看门狗被中止；任务结算后 5 分钟从 `tasks` 中清除。
