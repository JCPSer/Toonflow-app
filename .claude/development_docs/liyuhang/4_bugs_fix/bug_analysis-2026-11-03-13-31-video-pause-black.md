# Bug 分析：画布视频节点暂停后画面变黑

- 时间：2026-11-03 13:31
- 提出人：liyuhang
- 状态：待评审

## 1. Bug 矩阵

| 项目 | 内容 |
| --- | --- |
| 背景 | 用户在画布上逐个节点播放 AI 生成的视频，需要停帧核对画面（上一轮刚做过首尾帧 Y 轴拉伸的逐帧比对），暂停是最常用的操作 |
| 现象 | 画布视频节点（视频节点 / 视频生成节点共用的播放器）播放中点暂停，**不到 1 秒**画面区域变纯黑；节点标题、进度条、时间、音量、截帧按钮都正常，只有画面区黑 |
| 触发条件 | 仅「画布上的视频节点播放器」；暂停用播放器自带按钮 |
| 恢复方式 | 再点播放立刻恢复出画；没有报错提示，也没有媒体错误弹窗 |
| 出现时间 | 用户确认「一直就有」，不是最近改出来的回归 |
| 影响 | 无法停帧查看画面、无法对着帧判断衔接；截帧按钮仍可用，但体验上等于「暂停即失明」 |
| 优先级 | P2（不影响数据与生成，只影响预览体验，但直接卡住逐帧核对的工作流） |
| 难度 | 中低（改动集中在 `packages/nodes/videoNode/src/components/videoPlayer.vue`，需重建节点包） |
| 风险 | 低（不改媒体读取、不改输出值、不改服务端）；画布层新增一个覆盖元素，需确认不挡交互、不影响全屏 |

## 2. 已完成的取证与排除项

1. **不是「视频源被卸载」**：暂停只把 `playing` 置 false；`useLazyFileUrl` 的 `deactivate()` 只在闲置 30 秒（`idleDelayMs = 30000`，线上 `videoNode.umd.js` 里也确认是 `3e4`）后触发，且触发后显示的是首帧海报，不是纯黑。
2. **不是解码失败**：继续播放立刻恢复画面；截帧功能（走宿主 ffmpeg）一直正常。
3. **不是应用逻辑在暂停时改了 `src`/`poster`**：`@pause` 的处理器只有 `playing = false`；`src`、`poster` 在暂停时不变；重渲染只换播放/暂停图标。
4. **不是「<video> 在变换层里」的通用 WebKit 缺陷**：用最小页面在 Safari 复现同样的结构（父级 `transform: translate(...) scale(...)`、`el-card` 式 `overflow:hidden` + 圆角 + 阴影、`object-fit: contain`、`max-height: 240px`、`pointer-events: none`、dataURL 海报、暂停时改按钮图标），**暂停后帧保留**。
5. **不是 blob URL 的问题**：用本地 HTTP + `fetch → Blob → createObjectURL` 的 blob 源，暂停后帧同样保留。
6. **不是大分辨率 / 多视频并发**：用用户工程里真实的 1920×2560 H.264（8 MB）视频、4 路同时播放后一起暂停，帧同样保留；20 路同时播放后暂停也保留。
7. **自建 WKWebView（Swift + AppKit，`mediaTypesRequiringUserActionForPlayback = []`）** 加载上述页面，暂停后同样保留帧。

> 结论：外部环境全部无法复现，说明差异出在 Electrobun 托管的 WKWebView 实例（图层/合成路径与裸 WKWebView 不同），而不是页面结构、媒体编码或应用业务逻辑。属于「暂停后最后一帧没有被合成器保留」这一类的平台行为，继续深挖需要 Web Inspector 级观测，投入产出比很低。

## 3. 方案候选

### A. 暂停帧画布覆盖（推荐）

暂停时把当前解码帧 `drawImage` 到一张与视频等大的 `<canvas>` 覆盖层上并显示，播放时隐藏；暂停状态下拖动进度条，在 `seeked` 后重画。

- 依据：本仓库已有「暂停态 video 用 drawImage 取帧」的成功先例（截帧的 `loadFrame`/`nudgeFrame`，WKWebView 下可用），说明解码帧本身可取。
- 优点：与平台行为解耦，确定能显示暂停帧；不改播放/截帧/输出逻辑。
- 代价：暂停时多一次 drawImage（按元素尺寸绘制，几十毫秒内）；需要处理 `object-fit: contain` 的留白与 DPR；原生全屏态不覆盖（全屏用的是 video 自身，另议）。

### B. 只加图层提示（一行 CSS）

给 `video` 加 `transform: translateZ(0)` / `will-change: transform`，尝试让暂停帧停留在独立合成层。

- 优点：改动最小，零逻辑。
- 缺点：机制未验证，可能完全无效；`will-change` 本身在 WebKit 上有已知副作用（本仓库画布合成层开关即因此默认关闭）。

### C. 暂停时微扰 currentTime

暂停后把 `currentTime` 挪 1ms 再挪回，逼解码器重出一帧。

- 缺点：可能造成可见的跳帧/闪烁（10-40ms），与「停帧核对」的诉求冲突，不推荐。

## 4. 建议

采用 A；B 作为 A 的附带保险（同一次改动里加上，成本为零，若 A 的绘制路径出现意外，B 仍可能让原生帧显示）。
