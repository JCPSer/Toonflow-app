# Bug 分析：素材读取竞争与子 Agent 无上限扇出

- 时间：2026-11-02 14:20
- 提出人：用户（「如果有 Agent 在一直频繁占用素材库拿文件看文件，其他节点会受影响吗？会不会导致请求失败」）
- 状态：已排查，修复范围经用户确认

## 1. 背景与现象

用户观察到画布里有 Agent 长时间、高频读取素材库。担心这类负载会拖慢其他节点，或直接造成请求失败。此前的「工具界面加载失败：timeout exceeded」与画布保存失败也被怀疑与之相关。

## 2. 排查结论（代码依据）

| 编号 | 问题 | 依据 | 影响 |
| --- | --- | --- | --- |
| B1 | 同一素材被两个 Agent 同时读取时，后到者直接 409 | `modules/assetLibrary/assets/library.ts:402` 调 `lockWorkspaceFiles`；`modules/localRuntime/workspace/files.ts:89-98` 对路径及其祖先做全局占用判断，冲突立即抛 `文件正在使用` | 多节点同时看同一素材会直接失败；不是超时，是确定性报错 |
| B2 | 每次读取都整文件 `readFile` + 同步 sha256 | `library.ts:405-409`；上限 100 MB | 常见几 MB 素材单次仅几毫秒（实测 20 MB 读取+哈希约 10 ms），但并发读同一文件会重复读盘、重复哈希，放大 B1 |
| B3 | `subAgent` 一次调用无上限并行扇出 | `agent/tools/subAgent.ts` 用 `Promise.all(tasks.map(...))`，工具描述明确写「并发数不设固定上限」 | 单个 Agent 可瞬时制造任意数量的并行模型请求，抢占事件循环、内存与上游配额 |
| B4 | 前端工具界面列表请求没有超时与重试 | `packages/toolScaffold/src/client.ts` 的 `axios.get("/api/tools/renderers")` 未设 timeout | 主进程繁忙或连接池排队时，一次失败就把整个工具卡片打成「加载失败」，用户只能手动重试 |

补充事实（不作为本次改动）：
- 纯读取不触发素材库 watcher，不会强制刷新前端列表。
- 不同路径的读取互不阻塞；同一路径异步读容量为 64，写独占。
- 节点之间没有全局调度队列，失败面来自共享的事件循环、内存、浏览器同源连接与上游配额，而不是「素材库锁」。
- `revision` 是 SHA-256，用于防止覆盖并发修改（`library.ts:384-387`）。改成 size+mtime 会削弱正确性，本次不动。

## 3. 目标

1. 消除同一素材并发读取的 409，重复读取复用同一次在途结果。
2. 给 `subAgent` 单次调用的并行任务数设上限，保留排队执行。
3. 工具界面列表请求加超时与一次重试。
4. 不改动 `revision` 语义、不改文件锁语义、不改素材库 UI 行为。

## 4. 优先级与风险

| 项目 | 评估 |
| --- | --- |
| 优先级 | P1（B1 是确定性失败；B3/B4 是稳定性加固） |
| 难度 | 低 |
| 风险 1 | 共享在途读取后，单个调用方的取消不能中断其他人的读取 → 读取有 100 MB 上限且通常很快，接受；调用方仍会立即收到取消 |
| 风险 2 | 并发上限改变大量子任务的调度顺序 → 仅限制同时执行数，任务全部保留并排队，结果仍按原索引返回 |
| 风险 3 | 重试放大服务端负载 → 仅对无响应/超时/5xx 重试一次，4xx 不重试 |

## 5. 验收标准

1. 两个并发 `readAssetFile` 读同一素材都成功，返回相同 `revision`，且只发生一次读盘（日志/计数断言）。
2. 读取期间另一个调用方取消，取消者立即结束，另一个仍能拿到完整结果。
3. `subAgent` 传入 20 个任务时，任意时刻最多 8 个在运行，最终 20 个都有结果。
4. `/api/tools/renderers` 首次超时后自动重试一次；4xx 不重试。
5. 类型检查与构建通过，已有单测不回归。
