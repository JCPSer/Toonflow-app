# Bug 分析：6 个 Agent 并行时连接池耗尽，面板加载与画布保存卡死

- 时间：2026-11-18 15:10
- 范围：Agent 运行传输层（`/api/agent` NDJSON 流）、面板会话读取、画布保存

## 背景与现象

用户在画布上同时运行 6 个 Agent 时出现两类症状：

1. Agent 面板打开后一直停在「正在读取对话…」（用户描述为“会话加载中”）；
2. 画布保存报「画布保存失败」。

少于 6 个 Agent 时基本不出现；停掉任意一个运行后，积压的请求会立刻恢复。

## 根因

每个 Agent 运行都是一条长生命周期的 NDJSON 响应（POST `/api/agent`，整轮占用连接，20 秒心跳保活）。WKWebView/WebKit 对同一 origin 的 HTTP/1.1 连接上限是 **6 条**（项目里 `netProbe` 已按 ≥6 在飞请求告警，说明该上限此前已被观察到）。6 个 Agent 同时跑正好占满连接池：

- 打开面板的 `POST /api/agent/get`、画布保存的 `PUT /api/workspaces/files/write` 在浏览器侧排队，axios 未设超时 → 面板永远停在加载态；
- 保存请求长时间排不到连接或被底层断开 → 前端落到「画布保存失败」兜底文案。

因此不是服务端算力或业务逻辑损坏：直连 localhost 的其它接口正常，一旦释放一条流连接，积压请求立即完成。这是**传输层连接数**问题，不是后端通信内容问题。

## 影响

- 多 Agent 场景直接不可用（用户实际使用 6 个）。
- 面板、画布保存、其它工作区读写都可能被长流饿死；与 Agent 本身是否出错无关。
- 属于随并行度线性恶化的结构性问题，不是偶发网络抖动。

## 目标

1. 同一窗口内所有 Agent 运行复用一条长连接，UI 请求不再与 Agent 数量争抢连接池。
2. 保留既有事件语义：text/thinking/tool/question/canvasCall/subAgentEvent、done、error（含 EBUSY code）。
3. 停止、关闭面板、切换项目、页面刷新时能取消服务端运行，不留下孤儿任务。
4. 旧服务端（无总线接口）或总线建立失败时自动回退到原直连流，不破坏兼容性。

## 优先级

P0（阻断多 Agent 使用）。

## 难度

中。服务端新增总线与两个路由、主路由分流；客户端新增总线/分发/统一入口，改造两个调用点；保留直连回退。

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 总线断开导致所有运行一起失败 | 一次抖动影响全部 Agent | 客户端标记错误并主动 abortRun；下次运行自动重连；直连回退仍在 |
| 事件顺序/重复 done | 面板状态卡住 | 复用原 `send` 生成事件；done/error 只由运行收尾发送一次 |
| 停止语义丢失 | 服务端继续烧模型 | 中断时调用 `/api/agent/abortRun`；总线关闭服务端统一 abort |
| 多窗口共享一个 busId | 事件串台 | busId 由每个窗口独立生成；服务端按 busId 隔离 |
| 远程/代理模式不支持流式 | 总线不可用 | 保留 404 回退；远程连接沿用现有流式代理 |
| 服务端与 web 不同批部署 | 一半新一半旧 | 回退逻辑兼容旧服务端；部署要求同批同步入口与视图 |

## 验收标准

1. 6 个 Agent 并行时，打开新面板能正常加载，画布保存不报错。
2. 任一 Agent 停止/面板关闭后，服务端没有遗留活动运行。
3. 浏览器 DevTools 里 `/api/agent/bus` 只有一条长连接，Agent 数量增加不再增加长连接数。
4. 旧服务端（404）时行为与改动前一致。
5. 服务端单测、web 单测、构建通过；`netProbe` 在纯逻辑测试环境不再因 `window` 缺失报错。
