# Bug 分析：用户配置的模型窗口被内置表覆盖，自动压缩触发过晚

- 时间：2026-11-18 11:59
- 范围：`apps/server/src/modules/mediaGeneration/ai/index.ts` 的 `getModelLimits`，影响压缩阈值、上下文百分比、请求上限校验
- 现象来源：用户反馈「自动压缩有时没生效，Agent 报上下文已用尽，跑完三张也读不了、核不了」

## Bug 背景

Agent 会话默认开启自动压缩，触发点 = `窗口 - reserve`，其中 reserve 由压缩百分比与 `maxOutputTokens` 共同决定。模型窗口来自 `getModelLimits`：它先匹配硬编码 `modelContextLimits`，命中就直接返回，**不再看用户在该供应商模型里填写的 `contextWindow` / `maxOutputTokens`**。

用户的 `OpenCode-DP / deepseek-v4.1-flash` 显式配置了 `contextWindow: 512000`，但硬编码表把同一 id 写成 `1048576 / 393216`。于是：

- 压缩阈值按 100 万窗口计算：百分比 50% 时约 524,288，默认 80% 时约 655,360；
- 实际线路只有 512k，会话涨到 50 万时已贴近真实上限，压缩却还没到触发点；
- 模型在 ~49–50 万 token 时开始自述「上下文快用完」，随后拒绝继续读图核对；
- 会话记录显示 11-18 00:08 那个子会话峰值 503,206 tokens、期间无任何压缩记录，直到 03:46 才出现一次压缩；同一模型另一会话有 3 次压缩，所以是「有时生效、有时不生效」的阈值漂移，而不是功能完全失效。

## Bug 目标

1. 用户显式填写的 `contextWindow` / `maxOutputTokens` 必须真正生效，内置表只作为「用户没填」时的默认值。
2. 压缩阈值、上下文百分比、请求上限校验统一使用同一口径，不再出现两套窗口。
3. 保持现有配置格式与字段语义不变（留空＝用默认），不影响没有显式配置的用户。

## Bug 描述

| 编号 | 描述 | 影响 |
| --- | --- | --- |
| B1 | `getModelLimits` 的优先级是「硬编码表 → 用户值」，用户值永远被忽略 | 窗口被放大到 2 倍，压缩迟迟不触发 |
| B2 | `maxOutputTokens` 同样被硬编码覆盖，reserve 被抬到 393,216 | 触发点被进一步推后，百分比设置失真 |
| B3 | 跨供应商同名模型只做精确 id 比较，用户无法为「中转商实际更小」的窗口负责 | 用户只能改模型名或改代码 |
| B4 | 上下文百分比展示复用同一函数 | 用户看到的使用率被低估一半，误以为还有余量 |

## 优先级

P0（数据/体验双重问题）：直接导致长任务在关键步骤被迫中断，且用户无法通过设置自救（压缩百分比最低只能到 50%，按 1M 计算仍是 524k > 512k）。

## 难度

低。单函数优先级调整，加一个纯函数模块与单测；无数据结构变更。

## 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 用户填了明显过大的窗口 | 压缩更晚，可能撞真实上限 | 保留「正整数校验」；填入值即视为用户对该线路的声明，UI 已有输入说明；后续可加超限提示 |
| 用户只填窗口不填输出上限 | 输出上限回落硬编码表 | 两个字段独立解析，未填字段才回落，避免整条覆盖 |
| 内置表本意是防止错误配置 | 放宽优先级后失去保护 | 仅在用户**显式**填写时覆盖；留空行为完全不变 |
| 桌面端入口再次被错误产物覆盖 | 应用无窗口 | 部署只使用 `build:desktop` 的 tar.zst 负载，禁止用 `build:server` 产物 |

## 验收标准

1. `OpenCode-DP / deepseek-v4.1-flash` 的 `contextWindow` 解析结果为 512000，压缩阈值按 50% 计算约 256k。
2. 未填写窗口的模型仍按硬编码表/内置目录/262144 兜底，行为与现在一致。
3. 只填写窗口、不填输出上限时，窗口取用户值、输出上限回落默认值。
4. 会话涨到 30 万 token 左右能看到压缩，而不是等到 50 万。
5. 新增单测覆盖上述四种组合；服务端 typecheck 通过。

## 评审意见

| 评审人 | 意见 | 结论 |
| --- | --- | --- |
| 子 agent 评审 | 方向正确、实测 512000+50% 在 256k 触发；指出 P1-1「只填窗口时表内 393k 输出上限会把有效阈值钉在 50%，百分比设置失效」、P1-2 部署需按两层归档校验；P2：摘要预算与保留量叠加、横幅阈值用设置值、测试缺共识分支等 | 采纳 P1-1 文档化+测试固化、P1-2 部署校验；P2 全部处理（见方案实施修订） |
| 用户评审 | 通过（“继续”） | 通过 |
