# Bug 分析：桌面端点「立即压缩」约一分钟后必失败

- 时间：2026-10-31 11:58
- 模块：agent 手动上下文压缩（`apps/server/src/routes/agent/compact.ts`、`apps/web/src/components/agent/conversation.vue`）
- 环境：macOS 15.7 / Apple Silicon / `/Applications/toonflow-exec.app`（Electrobun + WKWebView，安装版）
- 对应方案：`bug_solution-2026-10-31-11-58-compact-60s-timeout.md`

## 一、结论先行

不是压缩逻辑失败，也不是上下文超长：**桌面端 WebView 的空闲超时是 60 秒，而大历史手动压缩实测要 48.6–69.8 秒，且这期间服务端一个字节都不发**。请求在约 60 秒处被客户端掐断，服务端收到连接关闭后按既有设计中止压缩，摘要被作废、会话文件没有任何写入。前端因为拿不到响应体，只能显示兜底文案「压缩上下文失败」。

服务端侧没有任何问题：同一份会话、同一个接口，用 curl 起隔离实例跑，三次都返回 200 并写出新摘要。

## 二、Bug 矩阵

| 编号 | 描述 | 背景 | 目标 | 优先级 | 难度 | 风险 |
| --- | --- | --- | --- | --- | --- | --- |
| B1 | 手动压缩是一次持续 60–70 秒、期间零字节输出的同步请求，被 WKWebView 的 60 秒空闲超时掐断；服务端 `close` 触发 abort，摘要作废且不落盘 | WebKit 把异步 XHR 超时夹到 60 秒上限，默认 `timeoutIntervalForRequest` 也是 60 秒；大历史摘要实测 48.6–69.8 秒；桌面端走 HTTP，自动压缩走进程内 | 压缩耗时超过 60 秒也能正常返回并落盘，界面提示「上下文已压缩」 | P0（功能完全不可用） | 低 | 中（改变响应时序，需确认失败路径与契约） |

> B1 修好后，业务类失败（对话正在运行、文件被占用、空摘要、模型不可用等）都会带具体 `message`；B2 只剩浏览器层断连（网络中断等）仍无文案，属预期。
> B3 不是缺陷，是有意设计：压缩一次约 130k tokens 的摘要请求，若客户端已走开还继续跑，会白烧 token 并占着会话文件锁。

## 三、现象

1. 在桌面应用 agent 面板点「立即压缩」。
2. 界面一直显示压缩中，约一分钟后弹出「压缩上下文失败」，没有其他文案。
3. 会话文件没有新增 compaction 记录，**也没有任何写入**（mtime 不变）。
4. 同样的会话、同样的接口，在服务端用 curl 直接跑是成功的。

「一分钟」这个数字本身就是线索：它和客户端的空闲超时重合，而不是和模型耗时、接口超时重合。

## 四、复现与排查过程

### 4.1 先排除业务错误

服务端每一种业务失败都有具体文案，且都通过 `message` 返回：

- 「对话正在运行，请先停止后再压缩」
- 「文件正在使用，请等待操作完成」
- 「上下文压缩失败：模型返回了空摘要，已放弃本次压缩」
- 「会话使用的模型不可用，请重新选择后再压缩」

而前端 `compactContext()` 的写法是：

```
data.code !== 200  → throw new Error(data.message || "压缩上下文失败")
catch (axios 错误) → error.response?.data?.message || "压缩上下文失败"
```

「压缩上下文失败」六个字**只在响应体里没有 `message` 时**出现——也就是连接层异常、空响应、非 JSON 这几种情况。排查方向由此确定：请求根本没走到业务失败分支。

### 4.2 服务端单独跑得通

用用户真实的三份约 8 MB 会话（`/Volumes/WD_BLACK_MAC/[0]【AI Art】/2026/蕾姆Rem/.agent/sessions/`）做隔离实例测试：端口 4011、独立 `TOONFLOW_DATA_DIR`、复用同一份 settings.json / providers，用 `POST /api/agent/compact` 直接调用。

结论：三次全部 HTTP 200，且三次都写出了新摘要。服务端逻辑与用户模型配置均正常。

### 4.3 在用户正在运行的应用服务上也跑得通

对用户正在运行的应用服务 `127.0.0.1:51766`（需带 `Origin` 头才会被认作本机请求）用同一份会话拷贝再跑：HTTP 200，耗时 66.6 秒，响应体 4.36 MB。

这说明不是「安装版服务端有问题」，差异只在**调用方**：curl 没有 60 秒空闲限制，WebView 有。

### 4.4 上下文并没有超长

实测该会话上下文 147,445 tokens / 512,000（28.8%），离上下文窗口上限很远。摘要请求本身约 130k tokens，这解释了为什么耗时会落在 60–70 秒，也说明「压缩失败」不是「装不下」。

### 4.5 实测数据汇总

| 场景 | 调用方 | HTTP | 耗时 | 结果 |
| --- | --- | --- | --- | --- |
| 隔离实例（4011，独立数据目录） | curl | 200 | 48.6 s | 写出新摘要 |
| 同上，第二份会话 | curl | 200 | 69.8 s | 写出新摘要 |
| 同上，第三份会话 | curl | 200 | 61.7 s | 写出新摘要 |
| 用户正在运行的应用服务（51766） | curl（带 Origin 头） | 200 | 66.6 s | 写出新摘要，响应体 4.36 MB |
| 桌面应用 | WKWebView / axios | 无响应体 | 约 60 s | 弹「压缩上下文失败」，会话无写入 |

三份真实会话的耗时有两次明显越过 60 秒，正好覆盖用户遇到的区间。

### 4.6 串起完整因果链

```
用户点「立即压缩」
  └ POST /api/agent/compact 开始压缩（预计 60–70 秒，期间零字节）
      └ 客户端空闲计时到 60 秒 → 断开请求
          └ 服务端 res.once("close") 触发 abortCompaction
              └ 摘要被作废，finally 里没有落盘
                  └ 前端拿到连接层错误，无 message → 「压缩上下文失败」
```

「用户点击后一分钟才失败」+「服务端没有任何写入」这两个事实，只有「客户端先放弃」能同时解释。

## 五、根因

1. **WebKit 的 60 秒空闲超时**：`URLSessionConfiguration.timeoutIntervalForRequest` 默认 60 秒，WKWebView 继承该默认值；WebKit 还把异步 XHR 的超时夹到 60 秒上限（WebKit r189445）。该超时衡量的是「多久没有收到数据」，不是「总耗时」。
2. **手动压缩恰好是一次长时间零输出的请求**：摘要调用在 60–70 秒内不向 HTTP 响应写任何字节，连接在客户端看来就是「无响应」，正好撞上空闲超时。
3. **服务端的断开处理放大了后果**：`compact.ts` 在 `res.once("close")` 时 abort。这是为了「用户走开就别再烧 token」的有意设计，但也意味着被掐断的压缩一定不会落盘——所以用户看到的是「失败且什么都没发生」。

补充：历史上手动压缩有时能成功，原因有二——自动压缩是在 agent 回合内进程内完成，不走 HTTP；上下文较小的会话能在 60 秒内出结果。

参考：Apple `timeoutIntervalForRequest` 文档；WebKit bug 163814 / commit 9504084；StackOverflow 63464690。

## 六、影响面

- **受影响**：桌面应用（Electrobun + WKWebView）内的手动压缩入口，凡是压缩耗时超过约 60 秒的会话都会命中；会话越大越容易复现。
- **不受影响**：服务端 API 直接用 curl / 其它 HTTP 客户端调用；agent 回合内的自动压缩（进程内，不走 HTTP）。
- **数据安全**：失败时会话文件保持原样，没有半截写入、没有损坏风险；代价是本次摘要请求消耗的 token 白费。
- **可观测性**：服务端日志只有正常的业务日志，没有异常栈——因为 abort 走的是既有路径，排查时容易误判为「前端问题」。

## 七、目标与边界

### 目标

1. 压缩耗时超过 60 秒也能正常返回，前端提示「上下文已压缩」，会话落盘。
2. 不改变前端调用方式与既有失败文案。
3. 保留「客户端断开即中止压缩」的省 token 取舍。
4. 不引入新的状态接口、不改成异步任务。

### 不做什么

- 不调整前端 `xhr.timeout` / axios `timeout`：已被 WebKit 的 60 秒上限挡住，无效。
- 不改成「异步任务 + 轮询」：要多一个状态接口和前端轮询逻辑，改动面大。
- 不改成「断开也继续跑完」：用户仍会看到报错，且与省 token 的取舍冲突。
- 不改 `compactAgentSession()` 的压缩逻辑本身——它已被证明是对的。
