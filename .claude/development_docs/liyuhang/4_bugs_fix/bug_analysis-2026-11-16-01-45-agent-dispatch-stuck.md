# Bug 分析：Agent 卡住，收不到其他 Agent 的消息

- 时间：2026-11-16 01:45
- 类型：派发队列卡死
- 状态：已修复，待重启验收

## 1. 现象

提示词审核员用 `sendToAgent` 再次派发，工具回执「已入队」，但目标节点一直停在等待输入，队列里的旧任务也不执行；再发相同的消息仍然没有反应。

## 2. 根因（两条叠加）

1. **running 表泄漏**：`runTask` 在注册 `running`/`runningNodes` 之后、进入 `try` 之前，会取画布上下文、解析会话模型。这一段任何一步抛错，`pump` 里的 `void runTask(task).catch(() => {})` 会把异常吞掉，`finish()` 永远不会执行——目标节点从此被当成「正在运行」，后续派活全部卡在队列；泄漏累计到 4 个还会占满全画布并发。
2. **去重键不释放**：同一对节点相同消息 60 秒内只接受一次；但键在任务结束后没清，导致「上一轮已完成，用户/上游再发同一条」被静默丢弃。工具侧只看到「已入队」，表现就是「没有任何反应」。

另外 `readLastAssistantText` 用了一个永不中断的 `AbortController`，本地接口挂住时 `finish` 也会被卡住，进一步放大问题 1。

## 3. 修复

- `runTask` 改为 `try / catch / finally`：取上下文、解析模型、读结果全部纳入保护，`finally` 里在 `running` 仍登记时调用 `finish`，保证释放。
- 模型解析与结果读取加超时（5s / 8s），本地接口不返回时也能走到 `finish`。
- `pump` 的兜底 `catch` 增加释放逻辑，防 `finish` 自身异常。
- 任务记录 `dedupeKey`，`finish` 时删除，去重只拦截「同一轮仍排队/运行中」的重复消息。

## 4. 测试

- 新增：同样派发在上一轮完成后可再次入队；取画布上下文抛错时节点被释放、后续排队任务仍能执行。
- `bun test agentDispatcher.test.ts`：7 pass / 0 fail。
