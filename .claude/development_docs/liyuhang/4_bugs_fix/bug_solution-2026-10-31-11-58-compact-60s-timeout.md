# Bug 方案：手动上下文压缩超过 60 秒被客户端掐断

- 时间：2026-10-31 11:58
- 对应分析：`bug_analysis-2026-10-31-11-58-compact-60s-timeout.md`
- 状态：已实现（仅服务端，前端零改动）

## 一、修复思路（结论先行）

问题的本质是「一次长耗时、零输出的 HTTP 请求」撞上了客户端的空闲超时。因此不需要把压缩变快，也不需要改协议——**只要让响应在压缩期间持续有字节流出，客户端的空闲计时就不会走到 60 秒**。

具体做法：接口在开始压缩前先写一个空格（JSON 允许前导空白），之后每 10 秒补一个空格，摘要完成后再把真正的 JSON 写进去并结束响应。HTTP 层面它仍然是一个普通的 `application/json` 响应，前端代码一行都不用改。

代价是首字节一发出，HTTP 状态码就固定为 200；失败只能靠响应体里的 `code` 表达。而前端本来就是先读 `data.code` 判断成败，所以这个代价对现有调用方不可见。

## 二、方案总览

| 子问题 | 方案 | 状态 |
| --- | --- | --- |
| B1 60 秒空闲超时掐断压缩 | 响应头发出后立即写空白，每 10 秒一次心跳，结束时写入完整 JSON | 已实现，typecheck 通过；流式复测 73.8 s 完整收包 |
| B2 失败时前端只有兜底文案 | 失败统一经 `errorFromCause()` 组装进响应体，业务失败都能带具体 `message` | 随 B1 一并解决 |
| B3 断连即中止、token 白费 | 保持现状（既有取舍） | 不改 |

## 三、详细设计

### 3.1 请求时序

```
POST /api/agent/compact
  │
  ├─ 解析工作区路径（失败仍走原有错误中间件，正常非 200）
  ├─ 注册 close / aborted → abortCompaction（保持不变）
  ├─ 设置 Content-Type: application/json、Cache-Control: no-store
  ├─ 立即写 1 个空格          ← 首字节，从这里开始客户端不再算「空闲」
  ├─ 启动每 10 秒一次的空白心跳
  │
  ├─ await compactAgentSession(...)   （60–70 秒，期间心跳持续写入）
  │     ├─ 成功 → body = success(结果)
  │     └─ 失败 → body = errorFromCause(错误)
  │
  ├─ finally：停心跳；摘掉 close / aborted 监听
  └─ 响应仍可写 → res.end(JSON.stringify(body))
```

关键点：

1. **首字节早发**：在 `await` 之前就把响应头和第一个空格发出去，客户端从此刻起持续收到数据。
2. **心跳间隔 10 秒**：远小于 60 秒阈值，留足抖动余量；每个心跳只有 1 字节，70 秒下来不到 10 字节。
3. **JSON 前导空白合法**：`" " + {"code":200,...}` 仍是合法 JSON，axios 解析不受影响。
4. **心跳与断开共存**：连接已断时写操作会被跳过或抛出，异常被吞掉，真正的清理仍由 `close` 事件里的 abort 负责；`finally` 一定会 `clearInterval`，不会留下孤儿定时器。

### 3.2 失败路径

```
compact 抛错
  → errorFromCause(error) 生成 { code, data, message }
  → 响应体写出，HTTP 仍是 200（首字节已发，无法再改状态码）
```

服务端既有的业务文案（对话正在运行、文件正在使用、空摘要、模型不可用等）全部由 `errorFromCause` / 原有错误对象携带，前端 `data.code !== 200` 分支会把 `message` 弹出来，行为与改造前一致。

对于「连接在压缩完成前就断了」的情况：响应已不可写，直接返回，不写半截 JSON。

### 3.3 为什么前端零改动

`conversation.vue` 的 `compactContext()` 只做两件事：

1. `data.code !== 200` → 抛 `data.message`；
2. axios 抛错（连接层）→ 用兜底文案。

改造后所有业务失败都走第 1 条，且带具体文案；只有真正的网络中断才走第 2 条。既有的成功处理（刷新消息、stats、contextUsage、提示「上下文已压缩」）完全不变。

### 3.4 与仓库既有做法的一致性

服务端已有同类「空白心跳防超时」的实现：`apps/server/src/routes/agent.ts` 与 `apps/server/src/routes/providers/debug/run.ts` 都是每 20 秒写一个换行。本方案沿用同一思路，只是把间隔收紧到 10 秒、且保持 JSON 契约（不改成 NDJSON）。

## 四、取舍表

| 方案 | 是否采用 | 原因 |
| --- | --- | --- |
| 空白心跳（本方案） | 采用 | 只改一个文件；保持 JSON 契约；前端零改动；不改变压缩逻辑 |
| 调大 `xhr.timeout` / axios `timeout` | 不采用 | 被 WebKit 的 60 秒上限夹住，配置无效；且桌面端默认就没有设置超时 |
| 异步任务 + 轮询 | 不采用 | 需要新增状态接口、任务表、前端轮询与清理，改动面远大于收益 |
| 断开后继续跑完、不中止 | 不采用 | 用户侧仍然会看到报错；且与「断开即省 token」的既定取舍直接冲突 |
| 改成 NDJSON / SSE 流式响应 | 不采用 | 也能解决超时，但必须重写前端解析；空白心跳已经够用，改动最小 |

## 五、改动清单

只改一个文件：`apps/server/src/routes/agent/compact.ts`。

| 位置 | 改动 |
| --- | --- |
| 导入 | 增加 `errorFromCause`（失败响应体构造） |
| 响应头 | 显式设置 `application/json` 与 `Cache-Control: no-store`，不再用 `res.json()` 一次性返回 |
| await 之前 | 立即写一个空格；启动 10 秒间隔的空白心跳 |
| try / catch | 由「直接 `res.json(success(await ...))`」改为「先算出 `body`（成功用 `success`，失败用 `errorFromCause`）」 |
| finally | 停心跳、摘掉 `close` / `aborted` 监听（原有的 abort 注册保留） |
| 结尾 | 响应仍可写时 `res.end(JSON.stringify(body))` |

前端、压缩逻辑（`apps/server/src/agent/runtime/sessions.ts`）、路由挂载均未改动。

## 六、兼容性与风险

| 项 | 说明 |
| --- | --- |
| HTTP 状态码语义 | 首字节发出后状态码固定为 200，业务失败改为 `body.code` 表达。仓库内该接口只有 `conversation.vue` 一个调用方，且它只读 `code`，无回归 |
| 响应体大小 | 仍是完整 JSON（实测约 4.36 MB），只多了几个空格字节 |
| 断连处理 | `close` / `aborted` → abort 的既有逻辑保持不变；心跳写入失败被吞掉，不影响 abort |
| 定时器泄漏 | 心跳在 `finally` 中清理；无论成功、失败、异常都会执行 |
| 错误中间件 | 工作区路径解析等「首字节之前」的错误仍走原错误中间件，状态码不变 |
| 代理 / 网关 | 桌面端是 localhost 直连，不经过会缓冲响应的代理；若将来把该接口暴露到跨网络代理后，需要复测心跳是否被缓冲 |
| 长尾耗时 | 心跳只解决「空闲超时」；若供应商侧本身超时或卡死，仍会失败，但那属于另一条错误路径，会带具体文案 |
| 回滚 | 单文件回滚即可，无数据结构变更、无会话迁移 |

### 7.2 流式复测（已完成）

用流式客户端对隔离实例复测，记录首字节时刻、每次收到 chunk 的时刻与间隔、总耗时、解析出的 `code`：

| 首字节时刻 | chunk 时刻与间隔 | 总耗时 | 解析出的 code | 是否落盘 |
| --- | --- | --- | --- | --- |
| 18 ms（响应头 17 ms） | 7 次心跳，间隔 10000–10003 ms | 73.8 s（已越过 60 s） | 200，382 条消息，响应体 3,248,063 B 且 `JSON.parse` 成功 | 是 |

另外在**真实渲染引擎**里复核过：同样的 WKWebView 探针，60 秒内零字节时 `xhr timeout 61009ms`、`fetch` 报 `Load failed`；改成「首字节立即发 + 每 5 秒一个空白」后跑到 85018 ms 仍 `load` 成功。即 WebKit 的 60 秒是空闲超时，数据流动会重置它——心跳方案成立，不是推断。详见 `3_test_results/2026-10-31-11-58-compact-60s-timeout.md` §2.1。
